# 本地安全运维 Agent：学习与优化路线

这不是“把所有 Agent 概念学完”的清单，而是一条把知识立刻落到当前项目里的路线。

每个阶段只完成一个闭环：**理解概念 → 改动项目 → 写测试/证据 → 能解释设计 → 再进入下一阶段**。

## 当前起点

你已经不是从零开始：项目已有工具白名单、参数校验、审批状态机、Named Pipe Broker 原型、混合检索、网络策略、系统检查和 13 项自动回归测试。

但它还缺少可量化的 LLM 工程、完整 Trace、RAG 评测、CI、可重复安装，以及真正的 Windows 服务/ACL 安全边界。因此未来 6–8 周不再优先增加工具，而是把已有能力做成可解释、可测量、可交付的工程能力。

```text
LLM 工程化
  → Tool / Skill 工程
  → Agent 架构
  → RAG 工程
  → Eval / 可观测性
  → 软件工程
  → 部署
  → 安全与交付
```

## 第一阶段：LLM 工程化调用

### 要理解的知识

- Provider 抽象：Agent 不应该依赖某个具体模型供应商。
- Structured Output：模型输出是待校验的数据，不是可直接执行的命令。
- 可靠性：timeout、retry、fallback、429/500、非法 JSON 和模型不可用都属于正常工程情形。
- 成本与延迟：模型调用是外部服务，应记录 model、输入/输出 token、耗时、估算成本、成功/失败。

### 在项目中怎么做

1. 建立 `core/llm/`，定义统一 `LLMProvider` 接口。
2. 将现在的意图解析迁移为严格 JSON Schema；解析失败回退到现有规则路由。
3. 增加 `LLMCallResult`：`success`、`data`、`error_code`、`latency_ms`、`usage`。
4. 用模拟 Provider 测试 timeout、429、500、非法 JSON、主模型失败后的规则回退。

### 证据

- `tests/test_llm_provider.py`
- `reports/llm-fallback.json`
- Trace 中可看到模型名、耗时、token、回退原因。

## 第二阶段：Tool / Skill 工程

### 要理解的知识

Tool 是受控能力，不是普通 Python 函数。每项能力应具有：名称、说明、参数 Schema、返回 Schema、风险级别、权限要求、超时和错误码。

```text
LLM / 规则路由
  → Tool 请求
  → Schema 校验
  → 风险与权限策略
  → 工具执行
  → 结果校验
  → 回答
```

### 在项目中怎么做

1. 将 `TOOL_FUNCS` 与 `TOOL_POLICIES` 合并为一个工具注册表。
2. 统一 `ToolResult`，不让工具直接向上抛未分类异常。
3. 为每个工具声明输入与输出 Schema；网络工具继续遵循白名单。
4. Skill 保持“发现/扫描/用户确认/安装”四步，绝不让 LLM 自动安装。

### 证据

- 参数非法、未知工具、越权动作、工具超时的回归测试。
- JSON 报告显示请求参数、策略结论和工具结果。

## 第三阶段：真正理解 Agent 架构

不要先加入多 Agent。先能解释当前单 Agent 的每个层负责什么：

```text
用户
 → Agent Runtime（一次任务的调度）
 → State（这一次进行到哪一步）
 → Router（选工具）
 → Policy（是否允许）
 → Tool / Broker（执行或申请审批）
 → Result（事实结果）
 → Answer（组织给用户的回答）

Memory：过去值得记住的事实
RAG：从知识库取相关材料
Broker：高风险动作的权限边界
```

### 在项目中怎么做

1. 在项目地图旁增加一张“单次请求时序图”。
2. 定义显式 `TaskState`，而不是只靠局部变量。
3. 把“解释结果”与“执行决策”分开：LLM 可以解释，但不能越过 Policy。
4. 只有出现真正可并行、独立、互不共享权限的任务时才考虑 Multi-Agent。

## 第四阶段：RAG 工程

### 要理解的知识

- Chunk：大小、重叠和文档结构会影响召回质量。
- Embedding：把文本转换为可比较的语义向量。
- Retrieval：Top-K、余弦相似度、metadata filter。
- Hybrid Retrieval：关键词与向量召回并行，再融合排序。
- Rerank：先从很多候选中取回，再用更精细方法选少量上下文。
- RAG Eval：不能只看“回答像不像对”。

### 在项目中怎么做

1. 建立 30 条运维知识问题，每题标注期望文档来源。
2. 测试 chunk size 为 200/500/1000 时的来源 Recall@K。
3. 比较关键词、向量、混合检索三种结果。
4. 后续再加入 rerank；不要先换向量数据库。

### 证据

```text
Question → expected_source → retrieved_sources → Recall@K → answer/faithfulness
```

## 第五阶段：Eval 与可观测性

当前 13 项测试是很好的起点，但它是回归测试，不是完整 Agent Eval。

### 要增加的四类数据集

```text
eval/
├─ routing_cases.json      # 意图、工具、参数
├─ safety_cases.json       # 注入、越权、重放、非法参数
├─ rag_cases.json          # 问题、期望来源、答案
└─ fault_cases.json        # timeout、工具错误、模型不可用
```

### 要记录的 Trace

```text
trace_id
用户输入摘要
→ LLM/规则路由（来源、耗时、token）
→ 参数校验
→ 检索结果标识
→ 工具调用（参数摘要、耗时、状态）
→ 审批状态
→ 最终结果
```

日志必须脱敏：不写 API Key、完整敏感路径或原始私密文档。

### 指标

- 工具选择准确率
- 参数准确率
- 高风险动作拦截率
- 未授权工具调用率
- 规则回退成功率
- RAG Recall@K / 来源命中率
- P50 / P95 延迟
- token 与成本

## 第六阶段：软件工程化

### 在项目中怎么做

1. 将配置分为 example、local、runtime；local/runtime 永不提交。
2. 将测试分成 unit、integration、security、eval。
3. 增加 GitHub Actions：每次 push 运行 `scripts/run_verification.py`。
4. 定义版本号、`CHANGELOG.md`、发布说明和 Issue 模板。
5. 只在测试通过后创建 Release。

## 第七阶段：部署

当前项目的 Broker 使用 Windows Named Pipe，因此 Docker 不能替代 Windows 安全边界验证。

正确顺序是：

1. 先完成 Windows 安装/卸载脚本、环境预检、配置检查和干净 Windows 11 复现。
2. 再用 Docker 容器化不依赖 Windows 权限模型的部分，例如 RAG、Eval 或 API 服务。
3. 学习 Dockerfile、环境变量、日志、卷、镜像版本与 secrets。
4. 若未来需要跨平台服务端，再部署到 Linux；Windows Broker 保持独立。

## 第八阶段：安全与交付

安全原则：**LLM 不是最终权限控制者。**

下一阶段的 Windows 安全边界：

```text
普通用户 Agent
  → 精确 ACL 的 Named Pipe
  → 独立服务身份的 Broker
  → 受 ACL 保护的审批库、策略、日志
  → 受限执行器
```

必须用反向攻击测试证明，而不是写在文档里：

- 普通 Agent 用户直改审批数据库失败。
- Agent 用户不能修改身份策略、Broker 或执行器代码。
- 未授权 SID 无法连接 Pipe。
- 用户 A 创建，用户 A 自己批准失败，用户 B 批准成功。
- 100 并发请求只有一个执行者。

## 每周节奏

```text
第 1 天：学习一个概念并写最小实验
第 2–3 天：把实验接入当前项目
第 4 天：补测试、故障用例和证据 JSON
第 5 天：更新项目地图、README、可靠性报告
第 6–7 天：复盘；只决定下周一个主题
```

## 暂时不要做

- 不要为了“像 Agent”而堆 Multi-Agent。
- 不要不断替换框架或向量数据库。
- 不要让 LLM 自动执行 Shell、安装 Skill 或修改系统。
- 不要在没有评测数据时宣称“优化有效”。
- 不要在 Windows Service、ACL 和跨身份验证完成前宣称生产级安全隔离。

## 最终目标

8 周后，你不只是能说“我做了一个 Agent”，而是能拿出：

```text
一个能安装与演示的产品原型
一套可重复运行的测试与 Eval
一份 Trace 与性能/成本证据
一条经过反向攻击测试的安全边界
一套能解释设计取舍的项目文档
```
