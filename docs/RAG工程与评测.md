# RAG 工程与评测

## 当前实验是什么

项目包含一套 Demo 运维知识库和 30 条人工标注问题。每题指定期望来源文件，而不是依据“回答看起来合理”打分。评测比较：关键词、运行时 embedding、关键词与向量的 RRF 混合检索；每组取 Top-3。

Agent 的 `query_knowledge` 和 Eval 现在共用 `core.rag.KnowledgeRetriever`。两者使用相同的标题感知切分、embedding 调用、关键词检索、向量检索和 RRF 混合排序，不再分别维护两套检索实现。个人历史记忆仍使用原来的 `vectors.db`，不属于这次调整范围。

```text
问题 → 期望来源 → 各检索器的来源列表 → Recall@1 / Recall@3 / MRR
```

运行：

```powershell
.\.venv\Scripts\python.exe scripts\run_rag_eval.py
```

完整逐题证据写入 `reports/rag_eval_latest.json`。

## 当前结果

在当前 30 条 Demo 数据、`top_k=3` 和运行时 embedding 入口条件下：

| Chunk 大小 | 检索模式 | Recall@1 | Recall@3 | MRR |
|---:|---|---:|---:|---:|
| 200 | 关键词 | 93.33% | 100.00% | 0.9667 |
| 200 | 向量 | 63.33% | 83.33% | 0.7333 |
| 200 | 混合 RRF | 86.67% | 100.00% | 0.9278 |
| 500 | 关键词 | 93.33% | 100.00% | 0.9667 |
| 500 | 向量 | 63.33% | 83.33% | 0.7333 |
| 500 | 混合 RRF | 86.67% | 100.00% | 0.9278 |
| 1000 | 关键词 | 93.33% | 100.00% | 0.9667 |
| 1000 | 向量 | 63.33% | 83.33% | 0.7333 |
| 1000 | 混合 RRF | 86.67% | 100.00% | 0.9278 |

## 怎样解读，而不是夸大结果

1. 三种 Chunk 大小都生成相同的 18 个 Chunk，因此没有形成有效的大小对照。该项结论是 `inconclusive（无法得出最佳值）`，目前只能证明评测管线能运行。
2. 关键词目前优于向量，是因为题目与 Demo SOP 共享许多明确术语，例如 DNS、SMART、Defender、C 盘。这个现象是合理的，不应强行宣称混合检索更好。
3. 向量和混合检索使用与 Agent 运行时相同的 `embed_text` 入口；模型不可用时会自动降级为稳定的 BLAKE2b 本地 embedding。报告必须结合运行环境解释，不能把降级结果写成 BAAI 模型成绩。旧版降级 embedding 使用 Python 进程随机 hash，已修复；旧 `vectors.db` 如含该版本向量，需要重新导入。
4. 混合检索 Recall@3 达到 100%，但首位排序不如关键词，下一轮应在更多、更长、术语重叠更强的真实 SOP 上调 RRF 权重或引入 rerank；现在不换向量数据库。

## 已知限制

- 内容是 Demo SOP，不能代替组织的真实运维规范。
- 指标只衡量“期望来源是否被取回”，尚未衡量回答是否忠实于来源（faithfulness）。
- 评测和运行时已经共用检索实现，但当前报告仍只测来源召回，没有经过 Router 和 LLM 最终回答阶段。
- 当前知识检索器在进程内缓存文档与 embedding；知识文件或配置变化后需要重启 Agent 或调用缓存重置函数。
- 后续应补充真实但脱敏的 SOP、跨文档问题、同义改写和无答案问题，再做 rerank 实验。
